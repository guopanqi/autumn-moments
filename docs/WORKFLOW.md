# GitHub-only workflow

## 人与 Agent 的分工

人决定体验方向、评估是否有趣、选择美术偏好；Agent 负责可编译的最小实现、迭代、代码审查和测试证据。无需用户本地文件与软件。

## 开发与验收顺序

1. 在 GitHub Issue 描述可观察的目标及其失败条件，例如“点击茶杯后人物真的拿起杯子”。
2. 创建短分支并做一项垂直切片；避免同时重写相机、存档和美术。
3. 使用 Codespaces 5173 实时查看；必要时贴截图和简短观察记录。
4. 使用 Pull Request 的 CI 自动 `npm run build`（TypeScript + Vite）。
5. 人工检查桌面 + 手机尺寸，确保光照变化和交互均可读。
6. 合并主分支后 Pages 工作流发布，检查真实 URL，再标记阶段通过。

**仅运行 GitHub Actions 并不等于完成视觉质量或可玩性验证。** 构建通过只能证明部分技术正确；关键动作需要实际浏览器试玩。

## 一次变更的质量清单

- 是否让玩家实际做了不同的事情？
- 视觉是否与现有场景一致？动作有没有“起因—接触—结果”的时间关系？
- 新参数是否应集中在 `art/style.ts` 或地点数据里？
- 是否引入未经登记许可的模型/字体/音乐？
- 是否造成 Pages 公开链接失效或静态 base path 问题？
- 是否对以后切换 GLB/Blender 形成障碍？

## GitHub Pages 首次启用

Pages 必须在 Settings → Pages → Build and deployment → Source 中选择 **GitHub Actions**，才能使用 `.github/workflows/pages.yml` 发布。本连接可提交工作流，但不能保证有修改仓库 Pages 设置的权限。页面地址预计为 `https://guopanqi.github.io/autumn-moments/`，只有部署成功才能作为已上线地址报告。

## 资产来源管理

首版全部使用原创代码生成的基本几何，没有复制其他仓库的场景或模型。未来每个外部素材记录：原作者、链接、许可证、是否允许商业/修改、下载或提交日期、版权署名要求；参考可看但源码不能在未经授权时复制。

## 以后何时引入 Blender

只有当程序角色已不足以表达目标动作、需要系统性骨骼绑定、精细家具建模或可控贴图时，才引入。开发主循环依然保持 GitHub-first，Blender 作为制作生产资产的工具而非运行时依赖。优先采用 `.glb` + 约定的单位/朝向/骨骼动作名，保留代码式场景配置。

## 自动浏览器验收（2026-10-30 新增）

`.github/workflows/smoke.yml` 在 GitHub Actions 上安装 Chromium / SwiftShader，运行 `npm run test:smoke`。它检查 WebGL 启动、公园→小屋场所切换、选择家具/旋转/放置、刷新存档恢复、撤销与再回公园，且将公园、小屋、布置完成时截图作为 workflow artifact 保存七天。

这是**自动回归**，不是视觉评审：它无法自行判断色彩、人物情绪和动作是否达到了参考图要求。无 CI 证据时不得宣称浏览器通过。测试 `?e2e=1` 参数开放只读/诊断用 World 对象给自动化查询并投影坐标，平常页面不开放。
